A. INITIAL PROJECT UNDERSTANDING
--------------------------------------------------------------------------------
1. Existing Architecture:
   - Domain: Government Welfare Scheme Assistant RAG application.
   - Vector Store: ChromaDB persistent client at ./data/ChromaDB with collection 
     'welfare_schemes' (cosine space, 2,306 chunks indexed).
   - Ingestion: PyMuPDF (fitz) extracts text and tables from 6 raw scheme PDFs in data/raw.
     Chunking uses RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=200).
     Embedding uses BAAI/bge-m3 SentenceTransformer (1024-dimension normalized vectors).
   - Retrieval: Two-stage hybrid search:
     a) Dense retrieval: BAAI/bge-m3 top-10 chunks from ChromaDB.
     b) Sparse retrieval: In-memory BM25Okapi top-10 chunks.
     c) Reciprocal Rank Fusion (RRF, k=60, top_n=10) merges BM25 and dense candidates.
     d) Cross-encoder re-ranking: BAAI/bge-reranker-v2-m3 re-ranks candidates to top-5.
   - Corrective RAG (CRAG) Workflow:
     LangGraph StateGraph with 16 nodes and conditional routing:
     - Document relevance grading via Groq LLM (>=0.70 relevant, 0.30-0.69 ambiguous, <0.30 discard).
     - Ambiguous passage refinement: 200-char splits re-graded.
     - Evidence sufficiency evaluation: judges if combined evidence can answer query.
     - Secondary fallback: Tavily web search with LLM query rewriting if local evidence is insufficient.
     - Abstention node: returns polite abstention if evidence remains insufficient.
   - Generator:
     Groq-hosted 'openai/gpt-oss-120b' LLM (temperature=0.2). Synthesizes answers using
     strict citizen-friendly instructions and source citations [Source: file.pdf, Page X].
   - API:
     FastAPI application in src/llm/app.py exposing POST /chat compiling and invoking the graph.

2. Relevant Files Inspected:
   - src/Ingestion/load_documents.py, chunking.py, embeddings.py, vector_store.py
   - src/retrieval/dense_retriever.py, bm25_retriever.py, hybrid_search.py
   - src/CRag/schemas.py, graph_state.py, retrieval_evaluator.py, knowledge_refinement.py,

3. Implementation Constraints Discovered:
   - DeepEval 4.3.1 defaults to OpenAI when initialized without a custom model, raising
     DeepEvalError if OPENAI_API_KEY is not set. All evaluation metrics required a dedicated
     GroqJudgeModel subclassing DeepEvalBaseLLM.
   - The Groq model 'openai/gpt-oss-120b' is a reasoning model returning both 'reasoning'
     and 'content'; token limits and JSON extraction required careful handling.
   - In src/retrieval/hybrid_search.py, line 6 had a lowercase 'use_fp16 = false' bug
     causing a fatal NameError upon import across all modules.


B. FILES CREATED
--------------------------------------------------------------------------------
1. evals/config.py
   - Purpose: Centralized configuration module for evaluation paths, Groq judge settings,
     timeouts, retry policies, and metric pass thresholds.
   - Main settings: PROJECT_ROOT, RESULTS_DIR, EVAL_JUDGE_MODEL_NAME, EVAL_MAX_RETRIES,
     CONTEXTUAL_RECALL_THRESHOLD, CONTEXTUAL_PRECISION_THRESHOLD, FAITHFULNESS_THRESHOLD,
     ANSWER_RELEVANCY_THRESHOLD, ANSWER_CORRECTNESS_THRESHOLD.
   - Integration: Imported by all evaluation and reporting modules.

2. evals/groq_model.py
   - Purpose: Custom DeepEvalBaseLLM wrapper providing native Groq connectivity for DeepEval.
   - Main class: GroqJudgeModel(DeepEvalBaseLLM)
     - Methods: load_model, generate, a_generate, generate_with_schema, a_generate_with_schema,
       supports_json_mode, get_model_name.
     - Features: Exponential backoff for rate limits, markdown fence stripping, JSON mode support.
   - Integration: Passed directly into DeepEval metrics as model=judge_model.

3. evals/dataset_loader.py
   - Purpose: Validates, loads, and normalizes golden dataset examples, mapping metadata to
     DeepEval LLMTestCase objects while preserving source document provenance.
   - Main class: EvaluationDatasetLoader
     - Methods: load_raw_dataset, get_validated_examples, create_deepeval_test_cases.
   - Integration: Supplies verified inputs to both retriever and generator evaluators.

4. evals/evaluate_retriever.py
   - Purpose: Independent retriever component evaluation module.
   - Main class/functions: RetrieverEvaluator, retrieve_chunks, calculate_hit_rate.
     - Metrics: Contextual Recall, Contextual Precision, Hit Rate@k (diagnostic).
     - Output: Records per-case scores, reasoning, provenance hits, and saves retriever_results.json.
   - Integration: Directly executes production hybrid retrieval (BM25 + Dense + RRF + Reranker)
     without invoking the generator.

5. evals/evaluate_generator.py
   - Purpose: Independent generator component evaluation module.
   - Main class/functions: GeneratorEvaluator, format_context_string, generate_production_answer.
     - Test A (Controlled Context): Evaluates generator with verified reference context.
     - Test B (End-to-End Context): Evaluates generator with actual retrieved context.
     - Metrics: Faithfulness, Answer Relevancy, Answer Correctness (GEval).
     - Output: Saves generator_results.json with both experiments cleanly separated.
   - Integration: Wraps production generator model and prompt template from src/CRag/graph_nodes.py.

6. evals/report_generator.py
   - Purpose: Reads evaluation JSON results and produces human-readable Markdown reports
     and summary data.
   - Main functions: build_and_save_all_reports, generate_retriever_markdown_report,
     generate_generator_markdown_report, generate_executive_summary_report.
   - Output files: evaluation_results/retriever_report.md, generator_report.md, summary_report.md,
     evaluation_summary.json.

7. evals/run_evaluation.py
   - Purpose: Unified CLI entry point for the evaluation suite.
   - Arguments: --all, --retriever, --generator, --mode [controlled|e2e|both], --sample-size N,
     --top-k K, --generate-dataset, --report-only.
   - Integration: Orchestrates dataset loading, evaluation runs, and report generation.

E. EVALUATION METHODOLOGY
--------------------------------------------------------------------------------
1. Dataset:
   - Source: 6 Government welfare scheme PDF documents in data/raw.
   - Extracted Golden Test Cases: 59 QA pairs in evals/dataset/golden_dataset.json.
   - Provenance Preserved: Source PDF filename, page number, chunk ID, and reference context.

2. Retriever Evaluation Methodology:
   - Evaluated component: Production hybrid retrieval pipeline:
     dense_search(k=10) + bm25_search(k=10) -> reciprocal_rank_fusion(top_n=10) -> reranker(top_k=5).
   - Metrics:
     a) Contextual Recall: DeepEval ContextualRecallMetric (measures if retrieved context contains
        facts necessary to answer expected_output).
     b) Contextual Precision: DeepEval ContextualPrecisionMetric (measures if relevant chunks are
        ranked higher than irrelevant ones).
     c) Diagnostic Hit Rate@k: Checks if the source PDF and page number exist in the top-k retrieved chunks.
   - Distinction: expected_retrieval_context (ground truth) vs. retrieval_context (actual retrieved chunks).

3. Generator Evaluation Methodology:
   - Evaluated component: Production generator prompt and model ('openai/gpt-oss-120b').
   - Test A (Controlled Context): Question + verified golden reference context.
     Tests generator accuracy when complete facts are present.
   - Test B (End-to-End): Question + actual retrieved chunks from hybrid retriever.
     Tests combined system behavior.
   - Metrics:
     a) Faithfulness: DeepEval FaithfulnessMetric (penalizes hallucinations unsupported by provided context).
     b) Answer Relevancy: DeepEval AnswerRelevancyMetric (evaluates alignment with user question).
     c) Answer Correctness: DeepEval GEval with factual correctness rubric comparing actual output to expected answer.

J. RETRIEVER OPTIMIZATION EXPERIMENT: CONTEXT-ENRICHED CHUNKING & CANDIDATE EXPANSION
--------------------------------------------------------------------------------
1. Architectural Changes Implemented (100% Non-Invasive):
   - Chunk Sizing: Increased from 500 characters to 900 characters (overlap 150) to prevent
     fragmentation of complex eligibility clauses and tabular criteria.
   - Context-Enriched Metadata Injection: Every chunk is prepended with a structured context header:
     "[Scheme: {scheme} | Document: {source} | Page: {page}]\n{chunk_text}"
     This provides critical scheme identification for both BM25 inverted index matching and
     dense vector semantic clustering (BAAI/bge-m3).
   - BM25 Tokenization Optimization: Replaced naive whitespace splitting with alphanumeric regex
     tokenization (re.findall(r'\w+', text.lower())) so that punctuation marks (e.g. "document?",
     "guidelines.") do not cause zero-keyword matching.
   - Candidate Pool Expansion: Expanded candidate retrieval depth from top-10 to top-20 for both
     BM25 and Dense search prior to Reciprocal Rank Fusion (top_n=20) and BGE-Reranker-v2-m3 scoring.
   - Isolated Storage: Experimental chunks are embedded into ChromaDB collection 'welfare_schemes_v2'
     (1,092 chunks), leaving the production collection 'welfare_schemes' (2,306 chunks) 100% untouched.

2. Files Created for Experimentation:
   - evals/experiments/improved_chunking.py: Implements context-enriched 900-char text splitting.
   - evals/experiments/ingest_improved.py: Memory-safe batch ingestion script for 'welfare_schemes_v2'.
   - evals/experiments/improved_retriever.py: Hybrid search adapter with expanded candidate fusion.
   - evals/experiments/compare_retrievers.py: Side-by-side A/B comparative evaluation runner using DeepEval.
